我最近在搞一个文件分发系统，有个需求挺头疼的：用户经常要校验几个G甚至几十G的大文件完整性，但网络不稳定的时候传到一半就断了，之前都是从头再来，体验很差。所以想做一个支持断点续传的文件哈希校验工具。

基本流程是这样的：客户端把文件按固定大小切分成块，比如每块4MB，然后逐块计算哈希值发给服务端。如果中间断了，下次启动的时候能从上次中断的地方接着来，不用重新算已经算过的块。支持MD5和SHA256两种算法，用户可以选。服务端保存每个文件的分块哈希记录，用文件路径和最后修改时间作为唯一标识。

有个细节要特别注意：文件可能在上次校验和这次校验之间被修改过，这时候必须全部重新校验，不能复用之前的进度。判断条件就是文件的最后修改时间变了就不认了。另外文件大小不是块大小的整数倍很常见，最后一块要按实际剩余的字节数来算，不能补零也不能多读。空文件也是个合法输入，直接返回全零哈希就行。

进度信息要能随时查询，服务端要提供一个接口返回当前文件已经校验了多少块、总共多少块、百分比进度，以及每一块各自的哈希值。校验完成之后服务端返回整文件的最终哈希，这个最终哈希是把所有块的哈希值拼接起来再算一次得到的，不是直接对整个文件算的。客户端拿到最终结果后跟本地直接对整个文件算的结果做对比，两边一致才算校验通过。

如果某一块算出来的哈希跟之前保存的不一样，说明这块的内容变了，需要标记出来并从这一块开始重新校验后面所有的块，因为中间被改过的话后面的块边界可能也对不上了。服务端要记录每次校验的起始时间和完成时间，方便排查问题。

核心功能实现为一个独立package。在此基础上写两个程序：服务端引用核心库对外提供HTTP接口，客户端是命令行工具通过HTTP调用服务端。服务端和客户端各自独立main包，请求响应格式定义放在公共包。核心库、服务端、客户端各按职责分文件。先go mod init再开发，go build ./...能编译通过。

本项目属于跨系统多模块架构。
