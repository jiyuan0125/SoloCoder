我要做一个JSON Patch工具，就是RFC 6902定义的那个标准。简单说就是对一个JSON文档做局部修改，不需要传整个文档，只传变更的部分。这个标准定义了六种操作：add、remove、replace、move、copy和test。

add操作在指定的JSON Pointer路径位置添加一个值。如果目标路径指向一个数组索引，就把新值插入到那个位置，原来的元素及后面的元素都往后挪一位。这里用的是"插入"而不是"替换"，这是很多人搞混的地方。如果索引等于数组长度，就是在末尾追加。索引不能大于数组长度，否则报错。如果目标路径指向一个对象中不存在的key，就新增这个key-value对。如果指向一个已经存在的key，就替换它的值（对象成员的add等同于replace）。

remove操作删除指定路径的值。删除数组元素时，后面的元素要往前挪，索引要重新排列。这意味着如果你有一个patch包含两个remove操作，第一个删了索引0的元素，那第二个操作如果也引用索引0，它删的其实是原来索引1的元素。很多实现会在应用每个操作后更新文档，所以操作之间的顺序很重要。

replace操作就是先remove再add，但它要求目标路径必须已经存在，否则报错。move操作把一个路径的值移到另一个路径，源路径的值会被删除，目标路径会得到这个值。move的源路径和目标路径不能相同，也不能有父子关系，不能把一个父节点移到它自己的子节点下面。copy跟move类似，但源路径的值保留不动，相当于复制一份到目标路径。

test操作用来做条件检查，如果指定路径的实际值跟patch里给的值不一致就报错，整个patch应用失败。test操作的比较是深度比较，两个JSON值必须完全相同才算通过。这里有个容易出错的地方：JSON里数字1和字符串"1"是不同的值，test必须严格区分类型，不能做隐式转换。另外test一个不存在的路径应该报错，而不是当作null来比较。

patch本身是一个JSON数组，数组中的操作按顺序依次应用。如果中间某个操作失败了，整个patch要回滚到应用之前的状态，不能出现只应用了一部分的情况。服务端提供一个apply接口，接收原始JSON文档和patch数组，返回应用后的文档。还提供一个validate接口，只检查patch是否合法但不实际应用，返回校验结果。

JSON Pointer（RFC 6901）的解析也要实现。路径用斜杠分隔，斜杠本身和波浪号需要转义，斜杠转义为"~1"，波浪号转义为"~0"。所以解析的时候要先替换"~1"为"/"再替换"~0"为"~"，顺序不能反。空字符串代表整个文档。还有一个特殊路径"-"，在数组中代表追加到末尾。

客户端要能从文件读取JSON文档和patch文件，调用服务端应用patch，然后把结果写回文件。还要支持dry-run模式，只显示会变成什么样但不实际修改。

核心功能实现为一个独立package。在此基础上写两个程序：服务端引用核心库对外提供HTTP接口，客户端是命令行工具通过HTTP调用服务端。服务端和客户端各自独立main包，请求响应格式定义放在公共包。核心库、服务端、客户端各按职责分文件。先go mod init再开发，go build ./...能编译通过。

本项目属于跨系统多模块架构。
