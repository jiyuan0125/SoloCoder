retry_scheduler.c 的 retry_scheduler_execute 函数有个返回值逻辑问题。当 HTTP 传输本身成功了（ret == HTTP_ALERT_OK）但服务端返回的状态码是非 2xx 且不在重试范围内（比如 400、403、405），result.last_error 仍然是 HTTP_ALERT_OK(0)，result.success 是 0。然后 push_alert_with_retry 里 return result.success ? HTTP_ALERT_OK : result.last_error，因为 result.last_error 是 0 所以返回了 HTTP_ALERT_OK。main.c 收到返回值 0 就认为推送成功了，实际服务端拒绝了请求。修复方法：在 retry_scheduler_execute 里，当 is_success_response 返回 false 且 should_retry 也返回 false 时，把 result.last_error 设成一个有意义的错误码（比如在 http_alert.h 里加一个 HTTP_ALERT_ERR_HTTP_FAILED = -15），这样 push_alert_with_retry 就能正确返回错误。另外 retry_scheduler_execute 里整体超时的检查是在 sleep 之前做的，sleep 之后再执行一次连接尝试，实际耗时可能超出 overall_timeout 配置值不少。在 sleep 之前应该再算一下剩余时间，如果剩余时间已经不够一次尝试了就直接放弃。
