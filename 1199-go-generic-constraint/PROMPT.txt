我想做一个Go泛型约束检查器和类型参数推断工具。Go 1.18引入了泛型，但泛型的类型约束规则比较复杂，写错的话编译器报错信息有时候不太好懂。我的工具要提前检查约束是否满足，并辅助推断类型参数。

核心功能：输入一个泛型函数签名和一组调用点，检查每个调用点的实参类型是否满足类型参数的约束。支持interface约束（如constraints.Ordered）、联合约束（如int|float64）、近似约束（如~int表示底层类型为int的类型都行）、带方法的约束（如interface{ String() string }）。

服务端接收泛型函数定义（JSON格式描述类型参数和约束）以及调用点信息，返回每个调用点的检查结果：通过、约束不满足（说明哪个类型参数不满足哪个约束）、类型推断失败。客户端从Go源码文件中提取泛型函数定义，手动指定或自动识别调用点。

类型推断的规则是Go泛型里比较复杂的部分。函数调用时如果省略了类型参数，编译器会从实参推断。但有些情况推断不出来：比如`func Foo[T any](x T) T`调用`Foo(42)`可以推断T=int，但`func Bar[T any]() T`调用`Bar()`就推断不出来因为没有实参。工具要模拟这个过程，能推断的给出推断结果，推断不出来的明确标注。

近似约束`~`是个容易搞错的地方：`~int`匹配int以及底层类型为int的自定义类型（比如`type MyInt int`），但不匹配底层类型不同的类型（比如`type MyInt64 int64`不满足~int）。工具要正确处理这个语义。联合约束`int|string`表示类型参数可以是int或string中的任意一个，但如果约束是`interface{ int | string }`那含义不同，这是带方法的联合约束。

核心功能实现为一个独立package。在此基础上写两个程序：服务端引用核心库对外提供HTTP接口，客户端是命令行工具通过HTTP调用服务端。服务端和客户端各自独立main包，请求响应格式定义放在公共包。核心库、服务端、客户端各按职责分文件。先go mod init再开发，go build ./...能编译通过。

本项目属于跨系统多模块架构。
