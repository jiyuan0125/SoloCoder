我们系统之间通信用的是自定义的二进制协议，每次协议有变更都要手动修改解析代码，很痛苦。我想做一个工具：用DSL定义二进制消息的格式，工具自动解析二进制数据为结构化的JSON。

DSL的设计要简洁实用。一个消息定义由多个字段组成，每个字段有名字、类型和可选的长度。支持的类型包括：uint8、uint16、uint32、uint64、int8、int16、int32、int64、fixed_string(N)（固定长度N的字节串）、var_string（变长字符串，前面2字节是长度）、bytes(N)（N字节的原始数据）、checksum（校验和字段，不计入解析结果）。字段之间按定义顺序紧密排列，没有对齐填充。

核心功能：解析DSL文本生成消息结构定义，用结构定义解析二进制数据，将解析结果输出为JSON。同时支持反向操作：给定JSON和结构定义，序列化为二进制数据。DSL解析时要做语法检查，字段名不能重复，类型必须合法，fixed_string的长度N必须为正整数。

服务端存储消息格式定义（DSL文本），提供parse接口（传入格式ID和二进制数据，返回JSON）和serialize接口（传入格式ID和JSON，返回二进制数据）。客户端支持parse、serialize、validate三个子命令。parse从文件读取二进制数据发给服务端解析，serialize从JSON文件读取数据序列化为二进制并保存到文件，validate检查DSL文本是否有语法错误。

DSL的解析器是整个工具的核心。用递归下降或者手写的状态机来实现，不要引入第三方解析器生成工具。DSL的语法示例：
```
message LoginRequest {
    uint8 version
    uint16 msg_type
    fixed_string(32) username
    fixed_string(32) password
    var_string extra_data
    uint32 checksum
}
```

解析器的陷阱在于变长字段的嵌套处理。var_string的长度字段占2字节（uint16 little-endian），后面跟着的是实际数据。解析时要先读2字节得到长度L，再读L字节作为字符串内容。如果二进制数据的剩余长度不够L字节，要报错并指出在哪个字段处截断。fixed_string(N)的长度N是固定的，如果实际数据不够N字节，用零字节补齐。

字节序统一用小端序（little-endian），这是网络协议里最常见的约定。但checksum字段特殊：它的值是对前面所有字段字节（包括长度字段）的简单求和（uint8溢出后取低8位），解析时自动验证，不匹配则报错。序列化时自动计算checksum并填入。

还有一个细节：DSL支持注释，用//开头到行尾。解析DSL时要跳过注释和空行。字段名只允许字母、数字和下划线，且以字母开头。message关键字后面跟消息名，消息名只允许字母和数字。

核心功能实现为一个独立package。在此基础上写两个程序：服务端引用核心库对外提供HTTP接口，客户端是命令行工具通过HTTP调用服务端。服务端和客户端各自独立main包，请求响应格式定义放在公共包。核心库、服务端、客户端各按职责分文件。先go mod init再开发，go build ./...能编译通过。

本项目属于跨系统多模块架构。
