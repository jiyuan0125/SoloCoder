微服务之间的错误传递一直是个让人头疼的问题。HTTP状态码、gRPC status code、业务错误码三套体系互相映射，经常搞混。我想做一个错误码生成器，从一个YAML定义文件中读取错误码定义，自动生成Go代码，包括错误码常量、错误类型、wrap/unwrap链式调用、以及到gRPC status和HTTP状态码的映射。

YAML文件里每个错误码包含：code（业务错误码数字）、message（默认错误消息）、http_status（对应的HTTP状态码）、grpc_code（对应的gRPC status code name）、category（分类，比如USER_ERROR或SYSTEM_ERROR）。工具解析这个YAML，生成一个Go文件，包含错误码常量、一个实现了error接口的错误类型（支持携带附加信息）、Wrap和Unwrap方法（用fmt.Errorf的%w格式）、ToGRPCStatus和ToHTTPStatus的转换方法。服务端提供HTTP接口上传YAML文件生成错误码代码。客户端是命令行，指定YAML路径在本地生成。

要处理的边界情况挺多的。YAML里可能定义了重复的code数字但message不同，需要报错而不是静默覆盖。grpc_code的值要校验是否是合法的gRPC status code名称（UNKNOWN、INVALID_ARGUMENT、NOT_FOUND、ALREADY_EXISTS、PERMISSION_DENIED这些），拼写错误要能检测出来。http_status也要校验范围（100-599）。Wrap的时候如果传入的err是nil，返回nil而不是一个包装了nil的错误，这是Go错误处理的基本约定。Unwrap链可能很长，调用errors.Is的时候要能沿着整个链正确匹配。有的错误码需要支持动态参数（比如"用户%s不存在"），生成的错误类型要支持用fmt.Sprintf格式化消息。category字段的值不区分大小写，统一转大写存储。YAML里可以给某个错误码加一个deprecated标记，生成的常量上方要加// Deprecated注释。如果YAML里没有定义某个常用的错误码（比如通用的INTERNAL_ERROR），工具应该给出建议而不是强制要求。

客户端生成的文件名为errors_generated.go，包名从YAML所在目录推断。生成的代码要有完整的包注释，说明这个文件是自动生成的，不要手动编辑。

核心功能实现为一个独立package。在此基础上写两个程序：服务端引用核心库对外提供HTTP接口，客户端是命令行工具通过HTTP调用服务端。服务端和客户端各自独立main包，请求响应格式定义放在公共包。核心库、服务端、客户端各按职责分文件。先go mod init再开发，go build ./...能编译通过。
