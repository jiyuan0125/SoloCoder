林业局那边有个林火巡护管理系统的需求交给我们团队，让我来出技术方案。后端选 Go，前端用 Vue。数据全部放内存管理。

系统管的是一片林场里的多个管护区域，每个区域有名称、面积（公顷）、主要树种、负责的护林员姓名和联系电话。护林员的日常巡护工作需要管理起来。管理员给每个护林员派发巡护任务，任务内容包括巡护区域、巡护日期、要求巡查的路线关键点（至少3个GPS坐标点）。护林员完成巡护后提交巡护报告，报告里记录实际走的路线点、发现的异常情况。异常情况分两类，一类是病虫害，记录病虫害类型（松毛虫、天牛、松材线虫等）、发现的树木数量、严重程度（轻度中度重度）。另一类是火险隐患，记录隐患类型（野外用火、电线老化、易燃物堆积等）和处理状态。所有提交的异常会自动生成待办事项，分配给对应区域的管理员去跟进处理。管理员处理完毕后标记待办为已解决，并填写处理措施说明。前端有待办列表页面，可以按状态筛选查看。

病虫害数据有指标聚合统计。前端可以查看整个林场或单个区域的病虫害统计数据，按月汇总，展示每月新发现的病虫害报告数量、涉及的树木总数、重度占比。这些聚合数据帮林业局掌握病虫害趋势，提前做好防治准备。前端还有一个区域健康度看板，根据各区域的异常数量和严重程度综合打分。

业务规则方面有几个坑要注意。巡护任务指派的日期不能是过去的日期，必须是今天或未来日期，否则接口拒绝创建并返回明确提示。巡护报告提交时实际路线点数量不能少于任务要求的路线关键点数量的一半，否则判定巡护不合格，报告仍然保存但状态标记为不合格。同一个位置的病虫害异常如果7天内已经被报告过，新报告仍然要记录但系统自动标注为重复上报，避免管理员重复处理，标注信息在前端可见。待办事项如果超过14天未处理，系统自动标记为逾期并高亮提醒。火险隐患类的异常优先级高于病虫害类，分配待办时火险隐患排在前面。巡护报告中如果异常情况列表为空，表示巡护一切正常，仍然允许保存。

Go 后端用标准库搭建 HTTP 服务，数据存内存，用结构化的 map 组织。Vue 前端用组件化方式开发，页面包括任务管理、巡护报告、异常处理、统计看板。前后端 JSON 交互。
