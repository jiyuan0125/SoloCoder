我们后端团队有十几个微服务，每个服务的API文档都是散落在各处，想做一个统一的API文档平台。Go后端加React前端，后端用Gin框架，前端用React加Redux，用react-syntax-highlighter做代码高亮。

项目结构：后端和前端分开两个目录。后端叫docs-server，前端叫docs-web。后端除了提供文档管理的API之外，还负责解析上传的Swagger/OpenAPI规范文件并提取API信息。

API文档管理：每个微服务注册后，管理员上传该服务的Swagger JSON文件（支持OpenAPI 3.0格式）。后端解析Swagger文件，提取所有的API路径、方法、请求参数、响应格式等信息，存入内存数据库。

在线调试功能是重点。用户在文档页面上可以直接发送API请求进行调试。前端提供一个请求构建器：选择HTTP方法（GET/POST/PUT/DELETE），填写请求URL，添加请求头和请求体（JSON格式，带语法高亮和格式化功能）。点击发送后，前端通过后端的代理接口转发请求到目标服务（避免跨域问题），后端返回响应状态码、响应头和响应体。

代码分析功能：后端解析Swagger文件时，统计每个API的标签（tag）分组情况、请求参数的类型分布（string/integer/boolean/array/object）、响应状态码覆盖情况（200/201/400/401/404/500分别有多少个API返回）。这些统计信息在前端展示，帮助开发团队了解API的规范性。

配置加载：API文档平台自身的配置（比如代理超时时间、最大请求体大小、Swagger文件大小限制）通过YAML配置文件加载。配置修改后支持热加载，不需要重启服务。

注意事项。第一，在线调试时代理转发请求时，后端要设置合理的超时时间（默认30秒），并支持前端自定义。如果目标服务不可达，要返回明确的错误信息而不是连接超时的通用错误。第二，Swagger文件解析要容错，很多团队的Swagger文件不规范（缺少required字段、格式错误等），解析失败时不能导致整个服务崩溃，要跳过有问题的API并记录警告。第三，代码分析中的请求参数统计只统计必填参数（required=true），可选参数不纳入统计。

前端页面：服务列表页、API文档浏览页（按tag分组展示，每个API有说明和参数表）、在线调试面板、API统计概览页。

后端预置3个模拟的Swagger JSON数据，每个包含10到15个API端点。
