上周值班被消息队列的问题折腾了一整晚。生产环境消息积压把内存吃满，消费者挂了重启之后偏移量丢了又从头消费，重复处理了一大堆订单。这次用 Spring Boot 彻底重写，把踩过的坑全考虑进去。

消息体大小必须管住——超过 1MB 的直接拒绝，返回 413 并附带说明，告诉调用方消息太大需要拆分或压缩。消息声明了 JSON 格式但内容解析失败的，返回 400 带上解析错误位置，方便排查是哪个字段出了问题。这两种校验在写入之前做，校验不过的消息不能进入队列。

生产者发送速度过快是个大坑。每个 Topic 配一个消息数上限，积压超过上限后新发送的请求进等待队列，不能直接丢弃。等待超过 30 秒返回 503，告诉调用方暂时发不了，让它自己决定是重试还是走降级逻辑。等待过程要异步实现，别把工作线程占满。

消费者断连后的偏移量处理是重中之重。每条消息确认消费成功后立刻把偏移量持久化到本地文件，追加写入，定期压缩避免文件膨胀。消费者重连后从文件读取最后确认的位置继续消费，不会重复消费也不会漏消费。如果消费者提交偏移量时传了一个不存在的 Topic，返回 404，别静默忽略——之前就是因为静默忽略了导致排查了好久。

Maven 构建，JDK 17，端口写在配置文件里。
