新版接口上线前要小流量验证，之前直接全量切换翻车了好几次。最严重的一次是支付接口灰度没做好，新版本有个 bug 导致部分用户无法支付，影响了整整两个小时。Spring Boot 写个金丝雀网关，按用户 ID 百分比分流。

分流逻辑是取模运算。配 10% 灰度就 ID % 10 == 0 的走灰度后端，其余走正式。灰度比例和用户 ID 都通过接口配置。ID 格式不做假设——可以是数字也可以是字符串，字符串的话先算 hash 再取模。

灰度后端和正式后端分别配。灰度后端不健康时自动回退到正式环境——灰度出了问题不能影响正常用户，这是底线。健康检查每 10 秒探测一次灰度后端，连续 2 次失败判定为不健康。恢复需要连续 3 次成功。健康状态变更时记日志。

管理接口配置灰度比例（0-100 的整数，超出范围返回 400）和后端地址。灰度比例设为 0 表示关闭灰度，所有流量走正式。修改灰度比例后记录操作日志：谁改的、从多少改到多少、什么时候改的。

查询接口返回当前灰度配置和分流统计：灰度和正式各处理了多少请求、灰度后端的健康状态。统计按分钟级粒度记录最近 1 小时的趋势。

端口用 server.port 配置，Maven 构建。
