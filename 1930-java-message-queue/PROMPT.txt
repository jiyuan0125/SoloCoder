上周支付组的人来抱怨，说他们订阅了订单消息队列，结果里面掺了大量退款和库存的事件，消费端写了一堆 if-else 过滤逻辑，代码又乱又难维护。其实这种事挺常见的——不同业务线往同一个 Topic 里塞消息，下游只想捡自己关心的那几条，但队列全量推过来，消费者只能硬着头皮全收再做筛选。

Spring Boot 搞一个带过滤能力的消息队列服务。消费者订阅的时候带上过滤表达式，队列在投递之前先匹配，不满足条件的直接跳过，消费 offset 照常往前推——同一 Group 里被过滤掉的消息等同于消费成功，不会堆积。

表达式这块有三种原子类型：Header 等于某个具体值（比如 region=cn-east）、Header 包含某值（比如 tags 含 "vip"）、消息体 JSON Path 匹配（比如 $.amount > 1000）。三种能用 AND 和 OR 自由组合，比如 region=cn-east AND $.type=payment。消费者中途想改过滤规则也行，调一下接口，改完之后下一条消息立刻按新规则生效，之前投递中的不受影响。

有个性能底线要守住——队列堆积超过一万条时，过滤判断的耗时不能明显上涨。换句话说，过滤逻辑的复杂度得是 O(1) 或接近 O(1)，不能每条消息都遍历一遍所有规则做全文匹配。

死信队列的消息也支持先过滤再投递，避免死信里混杂的无关消息又被消费端拒掉形成死循环。

接口：POST /queues/{name}/subscribe 创建订阅（带 filter），DELETE 取消订阅，GET /queues/{name}/subscriptions 查看订阅列表。消息投递用 POST /queues/{name}/messages。

Maven 构建，端口在 application 配置文件里指定。
