我们需要一个实时的日志查看工具，类似一个 Web 版的 tail -f。前端页面打开后选择要看的日志文件路径，服务端实时把新增的日志行推过来，前端在页面上展示，像终端那样一行一行往上滚。

用 Go 来写。服务端通过 HTTP 提供 WebSocket 连接，客户端连上后发送一个订阅消息，指定要 tail 的日志文件路径。服务端用 fsnotify 监听文件变化，有新内容写入就把新增的行推给所有订阅了这个文件路径的客户端。同时客户端可以发送过滤规则，比如只看包含 error 关键字的行，或者排除某些行。服务端在推送前做过滤，不匹配的行不发，减少网络传输量。还有一个高亮功能，客户端告诉服务端需要高亮的关键词，服务端在推送的每行日志里把匹配到的关键词用特殊标记包起来，前端拿到后渲染成不同颜色。

日志收集这块，同一个文件可能被多个客户端同时订阅，不能为每个客户端都开一个 goroutine 去读文件，那样文件描述符会耗尽。要做好扇出，一个文件一个 reader，多路分发。

文本统计功能也要有。客户端可以请求统计当前订阅的日志文件里各类日志级别的分布情况，比如 info 有多少行、warn 有多少行、error 有多少行。统计结果通过 WebSocket 返回。这个统计是基于服务端已经读过的所有行来算的，不是只算当前在线期间收到的行。

日志文件可能会被轮转，就是原来的文件被重命名为 .log.1 然后新建一个同名文件，这时候监听要跟着切换到新文件，不能还盯着旧文件读。日志行可能非常长，超过 1MB 的一行也要能正常推送，不能截断。过滤规则可能包含正则表达式，正则编译失败时要给客户端返回错误消息而不是 panic。高亮关键词如果是正则的特殊字符要做转义处理。
服务端同时处理多个连接时不能出现数据混乱。 打开文件后如果处理到一半出错，要确保文件句柄被正确关闭。
服务端的监听端口应该支持通过命令行参数或环境变量来指定，不要硬编码。
