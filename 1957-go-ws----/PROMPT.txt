我们容器平台的运维需要一个集中查看容器日志的服务。平台上跑了几百个容器，分布在多台宿主机上，运维想在一个 Web 页面上实时看任意容器的日志输出，还能按标签过滤。

用 Go 写这个服务。每台宿主机上跑一个日志采集 agent，agent 通过 WebSocket 连到中心服务，注册自己所在的宿主机名。同一个宿主机名重复注册返回 409，让旧连接断开还是拒绝新连接要有一致的策略。agent 发现宿主机上有新的容器启动时，自动开始采集该容器的 stdout/stderr 日志，并通过 WebSocket 实时推送到中心服务。容器停止时停止采集。

前端页面也通过 WebSocket 连到中心服务。运维可以选择查看某个容器的日志，容器不存在返回 404。也可以按标签选择一组容器，比如看所有 app=web 的容器的日志。标签过滤语法不对返回 400。选择后中心服务把匹配的容器的日志流实时推给前端。前端还能发送关键词过滤条件，服务端在推送前做过滤，减少不必要的数据传输。

配置加载功能。容器标签的配置不是写死在代码里的，是从一个 YAML 配置文件加载的。配置文件修改后服务要能热加载，不需要重启。配置文件格式错误时不影响当前运行的服务，记录错误日志即可。配置文件里定义了标签和容器名的映射规则。

日志收集这块，同一个容器只能被一个 agent 采集，不能重复。如果两个 agent 同时上报同一个容器的日志，第二个返回 409。如果 agent 断线重连，要能从上次断开的位置继续采集，不能丢失日志。中心服务要把收到的日志按容器维度缓存最近 1000 行，这样前端刚连上来时能立刻看到最近的历史日志。

日志行可能包含非 UTF-8 的二进制数据，不能因为编码问题导致整个推送流程崩溃。容器名可能包含特殊字符，WebSocket 消息里要做好转义。多个 agent 同时推送日志到中心服务时，要做好并发控制，避免数据竞争。前端取消订阅某个容器后，agent 还在采集，但中心服务不再转发，不能因为没人订阅就停止采集，因为可能随时有人重新订阅。标签过滤要支持 AND 和 OR 组合条件。配置热加载后旧的标签映射关系平滑过渡，正在订阅的容器如果在新配置里匹配到不同标签，要重新按新标签归类推送。

服务端端口通过命令行参数或环境变量指定。
