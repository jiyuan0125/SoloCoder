线上的老配置管理系统太难用了——改完配置直接推全量，有个字段写错了整个服务起不来，回滚还得手动改回来。tokio 重写一个配置校验发布器，把"先校验、再灰度、最后全量"这套流程做进去。

配置变更之前先过 schema 校验。Schema 定义了每个 key 的类型（string/number/boolean/array/object）、是否必填、取值范围、正则约束等。变更请求 POST /configs 里带着新值，系统先用 schema 过一遍——类型不对返回 422（比如应该是 number 但传了 string），必填字段缺失返回 422，值超范围也返回 422。错误信息精确到字段级别：哪个 key、期望什么、实际收到什么。

校验过了还能预览影响范围——GET /configs/{key}/impact 返回哪些服务用了这个配置项，变更后会影响多少实例。这个信息帮助判断能不能在工作时间推，还是得等到低峰期。

灰度发布流程——配置变更不是一把推全量，而是先推给一部分实例（比如 10%），观察一段时间确认没问题再全量。POST /configs/{key}/deploy?strategy=canary&percentage=10 发起灰度发布。灰度期间监控变更后的配置是否被正常读取、服务日志有没有异常。确认无问题后 POST /configs/{key}/deploy?strategy=full 推全量。灰度发布中的配置版本和全量版本分开管理。

配置版本历史保留最近 50 个版本，可以回滚到任意版本。端口通过 PORT 环境变量配置，Cargo build 能过。
