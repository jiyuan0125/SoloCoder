微服务之间直接 HTTP 调用耦合太紧了——订单服务要通知库存服务、积分服务、通知服务，任何一方改接口都得协调半天，有时候通知服务临时下线订单就跟着报错。Fiber 做事件总线把服务间通信解耦，发布者不用管谁在订阅。

事件发布到总线后异步分发给所有匹配的订阅者。发布者调 POST /events/publish，body 包含事件类型（比如 order.created）和 payload（JSON 格式的事件数据）。总线收到后不阻塞发布者，直接返回 202 Accepted，后台异步把事件推给订阅者。

订阅者可以按事件类型过滤——订阅时指定感兴趣的事件类型列表（比如只订阅 order.* 通配符或 order.created 精确匹配），还可以按 payload 里的字段过滤（比如 amount > 1000 的大额订单事件才推送）。过滤表达式用简单的 JSON Path 或字段匹配。注册订阅用 POST /subscriptions，传 callback_url、事件类型、可选的过滤规则。

分发失败的事件进重试队列——推送超时或返回非 2xx，最多重试 3 次，间隔递增（1 秒、5 秒、15 秒）。3 次都失败后标记为 dead_letter，不再重试。GET /events/dead-letter 查看死信列表，可以用 POST /events/dead-letter/{id}/retry 手动重试。

GET /events/stats 查看各事件类型的发布量、订阅者的成功/失败推送次数。GET /subscriptions 列出所有订阅者和各自的过滤规则。

端口走 PORT 环境变量，go build 能过、能跑起来就行。
