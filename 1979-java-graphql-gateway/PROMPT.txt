前端要的数据分散在五六个后端服务里——用户服务有用户信息、订单服务有订单列表、商品服务有商品详情。每个服务各自一套 REST API，前端一个页面要调 5 个接口然后自己拼数据，逻辑越写越乱。Netty 做 GraphQL 网关统一入口，前端发一个 GraphQL 查询，网关自动拆分到各个后端。

GraphQL 查询处理流程——前端发 POST /graphql，body 是标准 GraphQL 查询字符串。网关解析查询，按字段拆分到对应的后端服务。比如查询 { user { name } orders { id amount } } 拆成两个子查询分别发到用户服务和订单服务，拿到结果后合并成一个 GraphQL 响应返回。子查询并行发出，总耗时约等于最慢的那个后端。

Schema 自动拼接——各后端服务通过 POST /schemas 注册自己的 GraphQL Schema 片段，网关自动合并成统一的 Schema。合并时检查类型冲突——如果两个服务都定义了 User 类型但字段不一致，报错要求手动配置冲突解决规则。

查询深度限制防止恶意攻击——最大允许 5 层嵌套。比如 { user { orders { items { product { category { name } } } } } } 是 5 层，再深一层直接拒绝，返回 GraphQL 错误格式。复杂度也可以限制——单个查询解析出的字段总数不超过 100 个。

GET /schema 查看当前合并后的完整 Schema。GET /stats 查看 GraphQL 查询的统计——总查询数、平均解析时间、各后端服务的调用次数和延迟。

构建用 Maven，端口走默认配置文件。
