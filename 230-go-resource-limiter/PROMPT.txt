我们公司的对外 API 服务偶尔会被恶意大量调用（比如有人写脚本疯狂请求），或者上下游服务出问题的时候大量请求堆积到我们这里，导致我们自己正常用户也受影响。需要一套保护机制防止服务被打爆。具体需求：每个请求路径要能配置最大同时处理数，超过这个数的请求直接拒绝返回 429 状态码。不只是按路径限流，还要按用户限流——每个用户（根据 token 识别）每分钟最多调用某个路径 100 次。有些路径特别消耗资源（比如导出报表要查大量数据），并发限制要更严格，比如最多同时处理 3 个导出请求。限流规则要能通过配置文件动态调整，不需要重启服务。如果服务整体负载已经很高了（CPU 使用率超过 80% 或者内存超过 90%），所有路径的限流阈值要自动降低到正常值的 50%，等负载降下来再恢复。被限流拒绝的请求要记录详细日志，包含用户标识、请求路径、当前每秒请求数。限流判断本身要非常快，不能因为限流检查拖慢正常通过的请求。如果同一瞬间到达大量请求，要做到公平分配——不能让先到的几个请求把配额全部用完，后面的请求全被拒。帮我用 Go 实现这套请求保护机制。限流规则和阈值通过 YAML 配置文件管理，支持按路径前缀设置规则（比如 /api/export/ 下的所有路径都用更严格的限制）。提供一个 HTTP 管理页面实时查看当前的请求速率、被限流的数量、各路径的并发数。

代码按功能模块分文件组织——按路径并发限流、按用户速率控制、系统负载自适应降级、限流规则热加载各自独立文件。go build 能过。
