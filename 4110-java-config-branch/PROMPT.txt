还记得上周的灰度翻车吗？一个配置改了直接全量生效，30% 的用户受影响。从发现问题到回滚花了 20 分钟，这 20 分钟里交易掉了多少？Spring Boot 重写配置中心，这次必须把灰度发布和分支管理做好。

配置项有两个维度。环境维度——dev、staging、prod，不同环境有独立的配置值。灰度维度——给配置项打灰度标签，比如 canary=true。同一个配置项在灰度和正式环境可以有不同值。客户端请求配置时上报自己的环境标签和灰度标签，服务端匹配返回。匹配优先级：灰度精确匹配 > 环境匹配 > 默认值。灰度配置确认后手动合入正式环境，合入操作记审计日志。

配置变更历史完整保留。每次变更记录四项：操作人、操作时间、旧值、新值。回滚到任意历史版本只需调 POST /config/{key}/rollback?version=N。回滚本身也算一次变更，记入历史。版本号只增不减，不会因为回滚而回退。

客户端获取配置走长轮询。客户端调 GET /config?env=prod&labels=canary=true&timeout=30，服务端检查是否有匹配的配置。有就立即返回，没有就 hold 住连接最多 30 秒。30 秒内配置变更了立即推送，超时了返回 304 Not Modified。

配置项支持引用——用 ${other.key} 引用另一个配置项的值。写入时递归解析引用链，检测循环引用。循环了直接拒绝写入并返回引用链路径，比如 a → b → c → a。引用的配置项不存在也拒绝写入，避免运行时空指针。

workflow 管灰度发布审批流，publisher 管长轮询和推送，version 管版本历史和回滚，resolver 管引用解析和循环检测。Maven 构建，端口写在配置文件里。至于需不需要加审批工作流——先看这一版用得怎么样。
