光靠前缀匹配有时候不够——比如要把 /user/123/profile 改写成 /api/v2/users/123/detail，前缀搞不定路径中间的动态段。用 Rust tokio 做一个支持正则路由的反向代理，复杂场景也能对付。

每条规则包含正则表达式、目标上游地址和改写模板。正则可以捕获组，改写模板里用 $1、$2 引用这些捕获组来重新构造目标 URL。规则按注册顺序匹配，先中先得，匹配到第一条就不再往下找了。规则走接口管理，增删改随时来，改完立即生效不用重启。

匹配后按改写模板构造新 URL 转发到上游。改写时还能增删 Header——比如去掉 X-Internal- 开头的内部 Header 不让它们泄漏到外部。请求 Body 不做任何修改直接透传。

GET 请求的响应有 5 秒短缓存，Key 就是完整的请求 URL，命中直接返回不再转发。上游返回 5xx 的不缓存，避免错误响应被缓存住。router 管正则匹配和优先级排序，rewrite 管 URL 改写和 Header 处理，cache 管短期响应缓存，proxy 管实际转发。Cargo build，端口 PORT 环境变量。


正则表达式的性能要注意——编译后的正则缓存起来，不要每次请求都重新编译。匹配时设超时，防止恶意请求写一个指数级回溯的正则把 CPU 打满。规则数量有限制，最多 100 条，超过的注册时报错。
