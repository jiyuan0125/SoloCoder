"发布流水线"这个概念，架构组叫 pipeline，运维组叫流水线，新人写的文档叫部署流程——术语不统一，跨组沟通成本直线上升。

`glossary init` 在当前目录创建 `glossary.yaml`，每条术语含 `term`（标准名称）、`aliases`（别名数组）、`description`（一句话解释）。定义好之后，`glossary scan ./docs` 扫描所有 Markdown 文件，找出术语和别名的首次出现位置，输出 `glossary-index.json`，每条记录含 `term`、`file`、`line`、`context`（该行前后各 20 字符的摘要）。`glossary check` 校验文档一致性：某个术语的别名在非首次出现时被使用就报 warning。

术语变更要走流程：`glossary submit` 提交 → `glossary review --approve/--reject` 初审 → `glossary finalize` 复审通过。初审不过可以修改后重新 submit。状态存在 `.glossary-state.json` 里，字段 `status`（draft/pending/approved/archived）、`reviewer`、`timestamp`。

术语文件为空时 `scan` 输出 "no terms defined" 并 exit 0。docs 目录不存在 exit 1。纯标准库，go build 编译通过。
拆成至少三个 Go 文件：main.go 做入口和参数解析，核心处理逻辑独立一个文件，工具函数单独放。
