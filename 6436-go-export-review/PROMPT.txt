代码审计第一步就是检查导出符号——哪些该导出没导出、哪些不该导出却导出了、导出的有没有文档注释。之前人工审查一个包要半小时，现在想自动化。

痛点在于 Go 里一个函数首字母大写就是导出的，但很多内部辅助函数不小心大写了开头，或者公开 API 没写注释。工具要做的事：

扫描 Go 包下所有 .go 文件，收集所有导出的函数、类型、常量、变量。对每个导出符号做三项检查——有未导出字段但整体导出的 struct 给出提示、导出符号没有 godoc 注释（即函数/类型声明上一行没有 "// 函数名 ..." 格式的注释）标为 warning、仅被同包内使用的导出符号建议降级为未导出。

命令行：`exportreview scan <目录> [--check comments,usage,fields] [--severity warn|error]`。--check 指定检查项，逗号分隔，默认全部。--severity 控制最低报告级别。扫描完成输出表格：符号名、类型（func/type/var/const）、文件:行号、问题、建议操作。

扫描流程走四个状态：初始化→扫描中→分析中→报告生成。分析阶段发现问题则标记为异常状态，最终汇总异常数量。如果某个导出类型的依赖关系变了（比如它引用的类型被重命名），依赖图要重新计算，结果缓存到 .exportreview-cache.json。

目录不存在退出码 1，无 Go 文件退出码 0，有 warning 级问题退出码 0 但打印提示，有 error 级退出码 2。

不用第三方包，`go build` 通过就行。
项目要用多文件结构，入口文件、业务逻辑、数据模型分开放，别揉在一个文件里。
