重试逻辑到底有没有生效？每次都靠 guess，心里没底。这次搞个工具把重试行为彻底验证一遍。

`retry-tester serve --port 8080 --fail-count 3 --status-code 503` 启动一个模拟服务端，前 3 次请求返回 503，第 4 次开始返回 200。`--fail-count` 控制连续失败次数，`--status-code` 控制失败时返回的状态码（支持 500/502/503/504），还可以用 `--fail-type timeout` 切换为超时模式（不返回响应，等客户端自己超时）。

`retry-tester test --url http://localhost:8080/api/test --max-retries 5 --backoff exponential --initial-delay 100ms --target http://localhost:8080` 发送测试请求。这个子命令会先启动内部 mock server（或用 --target 指定外部 server），然后发送请求观察重试行为。`--backoff` 支持 fixed 和 exponential 两种策略，exponential 的倍数固定 2。输出每次重试的时间戳、延迟、HTTP 状态码。

最后汇总 JSON：`{ "total_attempts": N, "success": bool, "attempts": [{ "sequence": 1, "timestamp": "...", "delay_ms": 0, "status_code": 503 }, ...], "total_duration_ms": 1234 }`。如果 max-retries 用完了还是失败，success=false。重试之间没有 delay 或 delay 不符合策略，在 stderr 打 "warning: unexpected delay pattern"。

多个 worker 并发处理输入数据——如果指定了 `--requests-file requests.json`（包含 URL 数组），则并行测试多个 endpoint，并发度由 `--workers` 控制（默认 4）。Go 实现，只用标准库，交叉编译友好。
