OOM killer 又把 Java 进程杀了——日志翻了半天才找到原因，能不能自动化？解析系统日志中的 OOM 事件，找出被 kill 的进程和原因，输出历史记录。

三个子命令：`oom list -log /var/log/syslog -last 24h` 列出时间段内的 OOM 事件；`oom detail -id 0` 显示某次事件的详细信息；`oom summary -log /var/log/syslog` 输出汇总。list 输出表格 `TIME  PID  PROCESS  SCORE  REASON`，JSON 模式下 `{"events":[{"time":"...","pid":1234,"process":"java","score":800,"reason":"out of memory","killed":true}]}`。

日志文件编码自动检测，遇到二进制内容跳过。没找到 OOM 事件输出 `"no OOM events found in log"` exit 0。-last 支持 `1h/6h/24h/7d` 格式。解析失败行在 stderr 打印 `"warning: skipped malformed line 1234"`。summary 包含总次数、最常被杀的进程 TOP5、OOM 频率趋势。

按天折算费用的时候，不满一天按一天算，跨月的分段计算。CLI 用子命令组织：`tool group command subcommand`，支持三级。源文件修改后，之前基于旧文件生成的缓存要同步失效。已经在使用中的缓存可以继续。

Go 实现，只用标准库，交叉编译友好。
拆成至少三个 Go 文件：main.go 做入口和参数解析，核心处理逻辑独立一个文件，工具函数单独放。
