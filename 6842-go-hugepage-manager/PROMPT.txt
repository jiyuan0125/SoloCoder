上周数据库性能骤降，排查发现 Huge Pages 没配够，TLB miss 飙到 30%。DBA 手动算页数算错了两回，线上又抖了一次。得有个工具能看清当前透明大页和静态大页的配置，知道还有多少空闲页可用，然后给出合理的预留建议。

子命令设计：`hugepage status` 读取 /sys/kernel/mm/hugepages/ 和 /proc/meminfo，输出每个大页规格（2MB、1GB）的总页数、已用页数、空闲页数，表格格式，列是 Size/Total/Used/Free/Percent。`hugepage recommend --workload oltp` 根据工作负载类型估算建议页数，oltp 按缓冲池 80% 算，olap 按 60% 算。`hugepage set --size 2M --count 1024` 调整 /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages 的值，写之前先检查当前空闲页够不够，不够的话输出 warning 但继续执行。`hugepage diff` 对比当前配置和上次 set 的配置，输出变更明细。

文件可能很大，超过内存要能处理——用 bufio.Scanner 逐行读。扫描完成后自动生成 summary.txt 摘要文件。某些 /sys 节点可能不存在（容器环境），这种情况下该行输出 N/A 而不是报错退出。配置变更后要重新计算所有受影响的规则。已经执行完的规则结果不变——set 操作是幂等的，重复执行相同值不报错。

Go 实现，只用标准库，交叉编译友好。go build -o hugepage-manager 直接出二进制。退出码：0 成功，1 参数错误，2 权限不足（需要 root），3 内核不支持。
项目结构要分模块：主入口、核心处理逻辑、工具函数分文件组织，方便测试和维护。
