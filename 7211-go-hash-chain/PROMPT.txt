为什么单独做一个哈希链工具？因为审计要求日志条目要能验证完整性，一旦有人改了中间的某条记录，后续所有条目的哈希链都要对不上。Go 写一个 AES-GCM 文件加密解密 + 哈希链验证的命令行工具，密钥从密码派生（PBKDF2），大文件分块加密。

AES-GCM 加密：密码通过 PBKDF2-HMAC-SHA256（10 万次迭代、16 字节随机 salt）派生 32 字节密钥。加密文件格式：16 字节 salt + 12 字节 nonce + 密文 + 16 字节 authentication tag。大文件按 4MB 一块分块加密，每块有独立的 nonce，块之间通过哈希链串联——第 N 块的额外认证数据（AAD）包含第 N-1 块的密文哈希，这样删掉或篡改任何一块都会导致后续解密失败。

哈希链验证是另一套独立逻辑。输入一组有序的日志行，每行包含 `index`、`data`、`hash` 三个字段。第 0 行的 hash = SHA256(data)，第 N 行的 hash = SHA256(prev_hash + data)。`hashchain verify --input log.jsonl` 逐行验证，发现断裂就输出断裂位置和预期哈希值。这个功能不涉及加密，纯哈希运算。

消息处理这块——本工具不做消息队列，但内部有任务队列：加密、解密、验证三种任务各自排队，最多同时跑 4 个。关联操作？比如加密完成后自动触发哈希链计算，这属于任务间的依赖关系。

状态流转：证书从申请到过期那些状态在这里不适用，但任务有 `queued`→`running`→`done`/`failed` 的状态。`crypto` 包封装核心加解密和哈希链逻辑。

`go build` 能过，命令行工具能正常运行。
