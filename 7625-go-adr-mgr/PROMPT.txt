半年前决定用 gRPC 不用 REST，原因写在哪了？没人知道。新人入职三天就问这种问题，我只能尴尬地翻聊天记录。得搞个 ADR（Architecture Decision Record）工具，把每个架构决策的前因后果结构化存下来。

ADR 实体有 ID、标题、状态（proposed/accepted/deprecated/superseded）、上下文描述、决策内容、后果分析、决策日期、决策参与者、关联的替代方案 ID。数据存本地 JSON 文件，支持完整的增删改查。

添加 ADR 用 `add --title <text> --context <text> --decision <text> [--consequences <text>] [--participants <names>]`，初始状态 proposed。`accept <id>` 把状态改为 accepted，`deprecate <id>` 改为 deprecated。被替代的记录用 `supersede <id> --by <new-id>`，old-id 自动标记 superseded 并关联到 new-id，new-id 必须是 proposed 或 accepted 状态。

查询支持多条件筛选：`list [--status <status>] [--participant <name>] [--from <date> --to <date>]`。`show <id>` 显示完整信息包含关联链（如果被替代了，显示替代者；如果是替代者，显示被替代者）。搜索用 `search <keyword>` 在标题、上下文、决策三个字段做子串匹配。

配置方面，默认配置可以设置参与者的常用列表、存储目录等。`config set --default-participants <names>` 修改后自动刷新内存缓存，缓存存着最近查询的 ADR 列表，刷新时重新从配置文件读取。

- `add --title <text> --context <text> --decision <text> [--consequences <text>]`
- `accept <id>` / `deprecate <id>` / `supersede <id> --by <new-id>`
- `list [--status <status>] [--participant <name>]`
- `show <id>`：完整信息含关联链
- `search <keyword>`
- `config set --default-participants <names>`

Go 标准库实现，go build 通过。
不要写成一个 main.go 搞定所有事情。按职责拆文件：入口、解析、处理、输出分开。
