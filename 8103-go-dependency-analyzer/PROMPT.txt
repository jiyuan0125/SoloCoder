上周重构一个微服务，改了 A 包的一个函数，结果 B 包 C 包 D 包全报错了——包之间的依赖关系根本没有人说得清楚。

写个 Go 包依赖分析工具。微服务项目包太多，依赖关系混乱——A 依赖 B，B 又依赖 C，C 反过来依赖 A，循环依赖就这么悄悄地产生了。

扫描指定目录下所有 .go 文件，提取 import 关系（排除标准库包），构建包依赖有向图。图的数据结构用邻接表表示——每个包维护一个它直接依赖的包列表和一个被依赖的包列表。

能检测循环依赖——用 DFS 遍历图时维护访问栈，如果遇到已经在栈中的节点就说明有环。报告循环依赖的具体路径：A -> B -> C -> A。

还能列出每个包的直接依赖数（fan-out）和被依赖数（fan-in）。依赖数特别多的包可能是"上帝包"，被依赖数特别多的包改动影响面大。
用法：dep-analyzer ./project。输出依赖拓扑排序结果（合法的编译顺序），有循环依赖的话红色提示路径。也输出按 fan-out 和 fan-in 排序的包列表。
遇到异常情况输出清晰的错误信息到 stderr，带上上下文方便定位问题。
异常路径和正常路径都要考虑周全。
