项目做了两年，接口膨胀到 15 个方法——这算合理抽象还是过度设计？需要工具自动分析接口的使用率和抽象程度。

帮我实现一个 Go 接口使用情况的分析器——看看项目里的接口定义是否合理，有没有过度抽象或者设计不当。

扫描 Go 项目中所有接口定义，统计每个接口的方法数量和实现者数量。检测这些设计问题：

只有单个实现的接口——可能是过度抽象，直接用 struct 更简单。接口方法过多——超过 10 个方法的接口违反了接口隔离原则，应该拆分。接口方法混合——查询方法（只读）和修改方法（有副作用）混在同一个接口里，违反命令查询分离（CQS）。空接口 any 的滥用——interface{} / any 应该只在真正需要任意类型的场景使用（如 JSON 解析），不应该用在函数参数上。

还要分析接口在函数参数中的使用——好的设计优先接收接口而非具体类型（Accept interfaces, return structs 原则），检查是否违反了这个原则。

输出格式要友好可读，人类能直接看懂，不要一坨原始数据糊脸上。
