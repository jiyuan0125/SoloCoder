搜索引擎的查询速度几乎完全取决于 Posting List 的性能。一篇文档对应的 docID 列表用裸数组存太浪费空间——几十亿的网页，每个词的列表可能有几百万个 docID，而且是递增的整数，压缩空间巨大。

1. 压缩存储。对有序的 docID 列表做 delta 编码（存差值而不是原始值），再用 varint 编码差值。比如 [100, 105, 110, 200] 变成 [100, 5, 5, 90]，然后 varint 编码。解码时反向还原。这是工业界的标准做法。

2. 集合运算在压缩格式上直接做。两个 Posting List 做 AND（交集）——同时解码两边的 varint 流，用双指针找相同的 docID。OR（并集）类似，取两边的并集。NOT（差集）从一个列表中去掉另一个列表中的元素。这些操作不需要把整个列表解压到内存再运算，流式处理即可。

3. Skip Pointer 跳表优化。在长的 Posting List 上每隔 P 个 docID 存一个跳表指针（指向更高层的位置），做交集运算时可以先比较跳表指针跳过不可能匹配的大段数据。跳表间隔取 √n 或 128。

4. 迭代器接口。提供 Next()、Advance(target) 方法，支持从当前位置跳到目标 docID 或更后的位置。这样上层的查询引擎可以用统一的迭代器接口组合多个 Posting List。

Go 标准库，go build 通过。压缩率要明显优于裸 []uint32 存储。
