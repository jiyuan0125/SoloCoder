团队从 MySQL 迁到 MongoDB 之后以为不用防 SQL 注入了，结果安全审计一扫发现代码里全是 bson.M{"username": userInput} 这种写法。MongoDB 的查询语法是 JSON/BSON，攻击者传一个 {"$gt": ""} 进来就能匹配所有记录绕过认证，跟当年 SQL 注入一个套路。

用 Go 写一个 NoSQL 注入检测工具。扫描 Go 源码中的 MongoDB 查询模式，识别以下风险：bson.M 或 bson.D 直接拼接用户输入——检测 map[string]interface{} 或 struct 字段值来自函数参数但没做类型校验的地方；$where 字段使用字符串拼接——$where 可以执行 JavaScript，如果拼接了用户输入就等同于命令注入；$regex 注入——用户输入直接作为正则表达式，可能导致 ReDoS 或信息泄露；类型混淆——Go 的 interface{} 如果接受 JSON 解码后的 map，攻击者可以传 {"$ne": ""} 这种操作符对象。

安全查询构建：提供 SafeQuery() 函数，对用户输入强制做类型检查——只接受 string、int、float64、bool 这些基本类型，如果检测到 map 或 slice 类型就拒绝（因为这可能是注入的操作符对象）。白名单过滤：只允许指定的字段名出现在查询中。

输出格式：JSON 报告，包含文件、行号、风险等级（高/中/低）和建议修复方式。高风险是 $where 拼接，中风险是 bson.M 直接拼接，低风险是疑似但需要人工确认。
