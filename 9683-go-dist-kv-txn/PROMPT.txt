上个月我们的支付系统出了个事故：扣了用户钱包的钱，但订单状态没更新成功，导致钱扣了但订单还显示"待支付"。根本原因就是跨 key 的操作没有原子性保证。分布式事务确实是硬骨头，不过可以先做一个简化版练练手——用两阶段提交（2PC）保证多个 key 的读写要么全部成功要么全部回滚。

Go 实现一个简易的分布式事务协调器。模拟 3 个参与者节点，每个节点维护各自的 key-value 存储。协调者接收一个事务请求，里面包含多个 key 的读写操作（比如读 key-a、写 key-b、写 key-c）。第一阶段，协调者向所有参与者发送 prepare 请求，参与者检查自己负责的 key 是否可以执行（比如 key 没有被其他事务锁住），可以就回复 yes 并锁住相关 key，否则回复 no。第二阶段，所有参与者都回复 yes 就发 commit，有任何一个回复 no 或者 prepare 超时（比如 5 秒没响应）就发 abort，参与者收到 abort 后解锁并回滚。

需要处理的异常场景：某个参与者在 prepare 后、commit 前网络断了（协调者收不到响应），这种情况下协调者要有超时机制，超时后发 abort。参与者恢复后如果发现自己有 prepared 但未 commit 的事务，要能向协调者询问最终决定。事务状态要持久化到文件，重启后能恢复未完成的事务继续处理。
