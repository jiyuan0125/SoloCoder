消费者组重启之后，100 条消息被重新消费了一遍——因为 offset 没持久化，每次启动都从 0 开始。位移管理看着简单，但手动提交和自动提交的取舍、持久化的时机、启动恢复的逻辑都得想清楚。

Go 实现消费位移管理模块。核心数据结构：按 topic + partition + group 三元组存储 offset 值。提供 Commit(topic, partition, group, offset) 更新位移，Query(topic, partition, group) 查询当前位移。自动提交模式下，启动一个定时器，每隔配置的间隔（默认 5 秒）把内存中的最新位移刷到持久化存储。手动提交模式下，业务代码必须显式调用 Commit，适合那些"处理完数据库写入才能确认消费"的严格场景。

启动时从持久化存储加载上次的位移，消费者从 committedOffset + 1 开始拉取消息。如果找不到历史位移（首次消费），从最新位置开始（latest）还是从最早位置开始（earliest）——这个策略要可配置。位移回滚的场景也要支持：业务处理出错时可以 Commit 一个更小的 offset 回退消费位置。

用内存的 map 模拟持久化存储即可，key 是 "topic:partition:group"，value 是 offset。但接口设计要预留真实存储的后端——定义一个 Storage 接口，内存实现只是其中一个实现。位移的持久化操作要有错误处理——写入失败时不能静默丢弃，要打印错误日志并重试。

go build 能编译通过，写个简单的 demo：启动自动提交模式消费 20 条消息，5 秒后模拟重启，验证重启后从正确位置继续。
