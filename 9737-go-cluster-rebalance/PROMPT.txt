分布式缓存集群 3 个节点跑了半年，数据量涨到需要加第 4 个节点。但数据怎么分配？简单地 hash(key) % N 变成 hash(key) % (N+1)，几乎所有的 key 都要重新分配——迁移量太大，缓存全部失效流量直接打到数据库。一致性哈希解决了这个问题：加节点后只有约 1/N 的 key 需要迁移。

Go 实现数据再平衡工具。基于一致性哈希环：每个物理节点映射到多个虚拟节点（默认 150 个），虚拟节点均匀分布在 0-2^32 的环上。Key 也 hash 到环上，顺时针找最近的虚拟节点确定归属。新增节点时，只需从相邻节点迁移属于新节点的 key——具体来说，新节点的虚拟节点插入环后，顺时针方向到下一个虚拟节点之间的 key 都要迁过来。

计算迁移计划：RebalancePlan(existingNodes, newNode) 返回需要迁移的 key 列表——每个 key 的源节点、目标节点和 key 本身。执行迁移时可以控制速率——每秒最多迁移多少个 key，避免影响正常读写。迁移过程中读取请求要考虑数据可能在旧节点也可能在新节点——简单的方案是迁移期间双查（先查新节点，没有再查旧节点）。

展示迁移前后的分布对比——每个节点负责的 key 数量和占比。理想情况下 4 节点各约 25%。节点移除也支持：LeavePlan(removedNode) 计算被移除节点的 key 如何分配给剩余节点。

go build 通过。初始 3 个节点、1000 个 key，加入第 4 个节点后，展示只有约 25% 的 key 需要迁移（不是全部重新分配）。
