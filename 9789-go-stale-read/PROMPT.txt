先来看过期读是怎么发生的：主节点写入 key=x 的值从 v1 改成 v5，但某个从节点还没同步到 v5，客户端从这个从节点读到 v3——这就是过期读。在高并发场景下这个问题会被放大，严重的时候用户看到的数据可能差了好几个版本。用 Go 写一个工具来检测和规避过期读。

数据模型：主节点维护 (key, value, version) 三元组，写入时 version+1。从节点异步同步，各自有不同延迟。客户端读取时记录每次返回的版本号。

过期读的检测：客户端维护一个 per-key 的 maxSeenVersion。每次读取后比较返回的 version 和 maxSeenVersion——如果返回的 version < maxSeenVersion，说明发生了过期读（之前都看到更高版本了，怎么现在又变低了？），记录一次 stale read 事件。

规避策略的实现。策略一：读前验证——读之前先问主节点当前最新版本号，然后从副本读，如果版本不匹配就重试。策略二：直接读主——最简单粗暴，读请求全部走主节点。策略三：版本缓存——客户端记住每个 key 的最大版本，读请求带上最低可接受版本，不够新的副本不返回。

模拟 10000 次读操作（3 个副本，1 个从节点延迟较大），分别用无规避、读前验证、直接读主三种策略，统计过期读发生次数、平均读取延迟。

Go 标准库实现，go build 编译通过。
