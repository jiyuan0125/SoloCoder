先想一个场景：3 副本的写入中，副本 C 暂时挂了。写入不能等它恢复（会卡住），但又不能丢掉副本 C 该写的数据。Hinted Handoff 就是解决这个问题的——让另一个节点暂时"代管"副本 C 的写入，等 C 恢复后再转交回去。用 Rust 实现这套机制。

数据结构：每个节点除了存储自己负责的数据外，还维护一个 hints 列表——HashMap<TargetNode, Vec<(key, value, timestamp)>>。当正常写入流程中某个副本不可达时，协调者把属于该副本的数据暂存在自己的 hints 里。

写入流程的修改：协调者收到写请求后，向所有 N 个副本发送写入。如果某个副本超时（比如 500ms 没响应），协调者把这条数据记入 hints[target_node]。然后继续处理——只要 W 个副本确认就返回客户端成功（W 的计算不包含 hinted 的）。

Handoff 的交付：后台有个定期任务（比如每 30 秒），检查 hints 中每个 target_node 是否恢复了。如果通了，就把暂存的数据批量发给目标节点。发送成功后从 hints 中清除。交付失败不影响——下次继续尝试。
