分布式锁的 session 管理经常被忽略——客户端和锁服务之间的连接不是永远稳定的。网络断了算不算释放锁？重连后还能继续用之前的锁吗？Session 机制就是管理客户端和锁服务之间关系的。用 Rust 实现一个带 session 的分布式锁。

Session 的概念：客户端连接锁服务时创建一个 session（类似 ZooKeeper 的 ephemeral node）。session 有一个 heartbeat_interval（比如 5 秒），客户端定期发送心跳。如果锁服务在 session_timeout（比如 15 秒）内没收到心跳，认为 session 过期，自动释放该 session 持有的所有锁。

Session 和锁的绑定：客户端通过 session 获取锁，锁的持有者是 session_id 而不是 client_id。这样即使客户端重连（新的 TCP 连接），只要 session 还有效，锁就不会丢。重连后客户端恢复之前的 session（发送 session_id 和认证信息）。

锁的获取和释放都通过 session：TryLock(session_id, key) 检查 session 是否有效，有效才能操作。Unlock(session_id, key) 检查锁的持有者是否匹配 session_id。

Session 的恢复：客户端重连后发送 Recover(session_id) 请求。如果 session 还没过期，恢复成功，客户端继续持有之前的锁。如果已经过期了，返回 SessionExpired，客户端需要重新创建 session 并重新获取锁。

模拟：客户端获取锁后网络断开 10 秒（小于 session_timeout），重连后恢复 session 继续持有锁。然后模拟断开 20 秒（超过 timeout），观察锁被自动释放。
