上周线上告警了一波"用户看到的数据跟实际不一致"，排查下来发现是某个从节点延迟了 3 秒，读请求打到了那个慢节点上拿到的全是旧数据。业务方说能接受最多 1 秒的旧数据，但 3 秒不行。问题是我们之前根本没有量化过"数据到底有多旧"这个指标，自然也没法做针对性优化。

这个工具用 Rust 实现过期读（stale read）的检测和处理。每条数据写入时记录时间戳 write_ts，读取时可以配置可接受的过期阈值 stale_threshold。如果读到的数据 write_ts 距离当前时间超过阈值，标记为 stale read。统计接口返回最近 N 次读取中有多少次是 stale read、平均延迟多少。另外支持遇到 stale read 时自动从主节点重新读取并返回最新值（read repair），以及按 key 查看各副本上的时间戳差异。

过期读的频率取决于副本延迟和路由策略，正常系统中通常只占几个百分点，但网络抖动时可能飙升到 20% 以上。这个工具帮我们把这些数据暴露出来。

Rust 标准库实现，cargo build 编译通过。
资源用完及时释放——文件句柄、网络连接这些不能泄漏。
输入输出格式统一，JSON 或者结构化文本。
